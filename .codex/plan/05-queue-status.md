## 実現すること

来場者が自分の順番を確認し、スタッフが正しい待ち組数・人数・当日入場数を把握できる。Pushなしでも利用できる。

## 対象範囲と境界

公開待ち情報、自分の券の状態、組数/人数/推定時間、マイページ一覧、運営dashboard、SQL集約と再取得制御。

負荷の実測なしに応答時間改善率を約束しない。根拠となる時間設定がないときは推定分数を出さない。

## 単一Go配布・Push延期の反映

一般受付の初期リリースではポーリングを標準の状況確認手段とする。画面を閉じた状態の通知は提供しないことを利用者へ明示し、表示中/非表示/離脱/復帰で再取得の頻度や停止・再開を管理する。Pushへの切替を待たず、同一originのConnect-RPCで自分の券と運営の最新状態を確認できるようにする。

## 実装手順

1. 券枚数=組数とparticipant_count=人数を区別し、waiting/called/pendingの算入を仕様に合わせ統一する。一般受付1人とグループ/同時収容の計算を分ける。
2. 自分の券は02の検証済みパスに限定し、公開の待ち組数/呼出番号と別応答にする。画面の入力なし復元を接続する。
3. 全履歴への1+2NクエリをJOIN/集約へ置き換え、終了済み順位計算を省く。active更新と残す履歴を分離し、履歴を無制限に返さない。
4. 管理件数は入場明細の全取得を止めDB側COUNTで取得する。イベントのtimezoneで日付を区切り、イベント/窓口scopeを保つ。booth一覧N+1等も対象SQLで見直す。
5. 再取得は同時実行抑止・AbortSignal・最新応答だけの反映を備える。通信停止を表示し、非表示の対戦画面のポーリングを起動しない。

[DB設計の調査結果](../../.claude/reviews/review%252Fcode-review/db-security-review.md) の DB05 / DB07 を本機能の責務として扱う。

- 読取/集計/一覧の上限、query/lock/pool取得の予算を11の基準に合わせる。poolは既定で無制限と決めつけず、1instance上限×最大instance数と他処理の接続数で確認する。
- 03/04/08でDBが保証する人数・帰属・入場一意性を集計の前提にする。関係不一致を画面の集計コードだけで隠さない。
- 履歴取得/削除の選択条件を06と揃え、必要なevent/status/期限の索引を実行計画で評価する。すべてのFKに機械的に索引を増やす方針にはしない。

## 完了条件・検証
- [ ] 組数/人数/推定時間とpending/取消の扱いが、対象となる一般受付/グループ/同時収容の設定に一致する。
- [ ] 自分の券と公開待ち情報を分離し、他パス/eventを混ぜず、日付境界で管理集計が正しい。
- [ ] 履歴増加でもSQL往復数を抑え、全入場明細を取得せず件数を返す。query/lock/poolの予算で接続が回収される。
- [ ] ポーリングの重複/離脱後更新/古い応答反映を防ぎ、Push/SWなしで呼出し表示と復帰時の再取得が動く。
- [ ] 期限切れ・削除済みfixtureで一覧/cacheに個別情報を出さない。06の実削除jobとの結合は06の完了時に確認する。

## 責務と有効化条件
