## 実現すること

希望する来場者だけが呼出し通知を受け取れ、通知が使えない人も受付を完了できる。

## 対象範囲と境界

購読/解除、成功・失敗表示、呼出イベントからの通知記録、宛先制御/timeout、claim/lease、失効・削除との連携。

Push許可・対応ブラウザを発券の前提にしない。対戦通知は08を有効にする場合だけ接続する。完全なexactly-onceは保証しない。

## 依存関係

- 一般受付のPush無効化は01/02/03/04/11-Eで完了する。09の完成を一般受付やCI/CDの条件にしない。
- 08を有効にする場合だけ対戦との通知結合試験を追加する。通常呼出しのPush導入に08全体の完成は要求しない。

## 単一Go配布・Push延期の反映

本機能は明示的に後続リリースへ延期する。初期の一般受付およびGo単一配布の完成条件には含めない。初期リリースで行うのは、購読UI/API・配信worker・通知enqueue・不要なService Worker登録を無効化し、主要受付が画面再取得だけで成立する確認まで。VAPID鍵を初期リリースの必須環境変数にしない。

後に導入するとき、Goの単一公開originと既存Connect-RPCを維持する。Push用のpublic設定を環境別buildへ埋め込むか、秘密値を含まないruntime設定にするかはその時点で決める。Cloud Runのbackground実行条件・必要なworker配置を検証し、SQL claim/lease・timeout・宛先保護が揃うまで有効化しない。既存Push利用者の扱いは切替時に明示し、延期を修正済みとみなさない。

## 実装手順

1. 無効時は購読API/workerと関連UIを停止する。有効イベントの有効パスで本人の購読だけ変更し、拒否/未対応/スキップ/登録失敗/成功を画面で区別する。
2. providerのHTTPS方針、接続時のprivate/link-local拒否、DNS/redirect制限を送信用transportへ実装する。各送信に期限/HTTP上限を設け、停止endpoint後も後続へ進む。
3. 通常呼出しと対戦呼出しで、実際に遷移した券だけに通知記録を作る。状態更新との原子性やイベントID/重複キーを検討し、再試行で不要な通知を増やさない。
4. 通知行を原子的にclaimし、processing/leaseとクラッシュ回収を設ける。外部送信中はDBロックを保持しない。終了/失効/削除済み対象への配信を止める。
5. 購読秘密値をログ/CSVへ出さず、06の期限削除へ接続する。サービスworkerのリンク先でもパス検証を保つ。

## DB設計調査の反映

[DB設計の調査結果](../../.claude/reviews/review%252Fcode-review/db-security-review.md) の DB05 / DB06 / DB07 を本機能の責務として扱う。

- endpoint/auth情報は配信に必要な読み戻せる秘密情報として扱い、09の処理と必要なDB権限だけに限定する。単純な全項目ハッシュ化はせず、購読のハッシュ識別子と送信用データを使い分ける。
- HTTP errorの文字列にはendpointの秘密pathが含まれ得るため、error_messageへ保存する前にエラーを分類しURL/認証情報を除去する。理由コードと必要最小限の補足、保存長上限を定める。先頭30文字の切り取りだけを安全なマスクとみなさない。
- 通知row/購読/券のevent・受付主体の帰属を保証する。claim/lease/期限削除の選択索引を実行計画で検証し、送信中のDBロックを保持しない。
- request/worker/queryの実行予算と接続数を11へ合わせ、06の失効/削除と競合しても秘密値の再保存や不要送信が発生しないようにする。

## 完了条件・検証
- [ ] Push無効/未対応/拒否でも取得→状況確認→入場が通り、失敗/スキップを有効表示しない。
- [ ] 内部宛先、内部redirect、DNS変化を拒否し、無応答先から期限内復帰する。
- [ ] 2workerの同時配信を抑えlease回収できる。通常/有効な対戦の呼出しで通知記録1件、終了・削除後に不要配信しない。
- [ ] 接続失敗等のHTTP errorを与えてもendpointの秘密pathやauth値がDBの失敗記録/ログ/CSVへ残らない。
- [ ] 失敗理由の保存長・再試行・lease期限・削除対象のevent境界が守られる。
- [ ] 09の有効化時に既存の一般受付を回帰検証し、Push無効イベントでは鍵/UI/API/worker/通知enqueueを使わない。初期無効化自体の完了は01〜04/11-Eで判定する。

## 責務と有効化条件

初期のPush無効化は01のflag、02の購読入口、03/04のenqueue無効、11-Eの起動/SW制御が所有する。09は後続の有効化・送信境界・queue・新データ削除を所有する。元のF02/F12/F15/F18/F19は有効化まで未解決として記録し、一般受付の無効化確認と区別する。

## 移行・分割方針

購読と表示→安全な送信→通知生成→queue claim/回収の小変更に分け、全完了まで新しい一般イベントでPushを有効にしない。08との結合テストは対戦利用時だけ追加する。
