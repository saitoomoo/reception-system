# Shared Coding Conventions

フロントエンド・バックエンドを問わず適用される共通の規約をまとめたものです。

---

## 1. コメント方針

### 原則: コードで表現できるなら、コメントは書かない

コメントが必要だと感じたら、まず以下を試す:

- 変数名・関数名を改善する
- 関数を分割して名前で意図を表す
- 型を追加して制約を表現する
- それでもなお説明が必要なら、コメントを書く

### 書いて良いコメント(why コメント)

- なぜそうしたか(過去の議論、業務背景、制約)
- なぜ別の方法を取らなかったか
- 一見不自然に見えるコードの理由(回避策、互換性対応)
- 外部仕様への参照(RFC、API ドキュメント、issue 番号)

例:

```ts
// Old API treats null as empty string. Match this during the migration period.
const displayName = user.name ?? "";
```

### 書いてはいけないコメント(what コメント)

- コードを日本語で言い直しただけのもの
- 関数名や変数名と同じ内容を繰り返すもの

NG 例:

```ts
// ユーザー名を取得する
const userName = user.name;
```

### 例外: 公開 API の関数ドキュメント

- ライブラリ的に使うパッケージの公開関数には godoc / JSDoc を書く
- 引数・戻り値・副作用を明記する
- これは「使う側が読む」ためのもので、「実装を説明する」コメントではない

### TODO コメントのルール

- `TODO:` ではなく `TODO(<担当者またはissue番号>):` とする
- TODO のまま 1 ヶ月以上放置されているものは issue 化または削除する

## 2. テスト全体方針: テストトロフィー

### テストの粒度バランス

- **静的型チェック + Lint**: 大量に依存(TypeScript の strict、Go の vet/staticcheck)
- **Unit テスト**: 純粋なロジック関数のみ(バリデーション、計算、変換等)
- **Integration テスト**: ★中心。handler から repository、実 PostgreSQL まで通す
- **E2E テスト**: 5〜10 シナリオ(主要動線のみ)

### カバレッジ目標

- **数値目標は設定しない**
- 代わりに「何をテストすべきか」を明示する:
  - すべてのハンドラに対して happy path の Integration テスト 1 本
  - すべてのハンドラに対してエラーケースの Integration テスト 1 本以上
  - ビジネスロジックを含む関数の Unit テスト
  - カスタムフック(state を持つもの)の Unit テスト
  - 主要動線の E2E テスト(5〜10 シナリオ)

### AI コーディング時の運用ルール

- 重要箇所を実装するときは、Claude Code に「先にテストを書いてください」と明示する
- テストアフターのときは、Claude Code が書いたテストが**実装の振る舞いをコピーしただけ**になっていないか確認する
- 「実装の正しさ」ではなく「実装の実装通り」を検証するテストは削除する

詳細は @docs/coding/frontend.md と @docs/coding/backend.md の各テスト節を参照。

## 3. ロギング全体方針

### ログレベルの使い分け

| レベル | 用途 |
|---|---|
| `DEBUG` | 開発時の詳細トレース。本番では出さない |
| `INFO` | 通常運用で残したい操作ログ(ユーザー作成、注文確定 等) |
| `WARN` | 失敗ではないが注視すべき事象(リトライ発生、想定外の入力 等) |
| `ERROR` | 処理失敗。エラーレスポンスを返すケース |

### フォーマット(Go 側)

- 環境変数で切り替え:
  - `APP_ENV=production` → JSON
  - それ以外 → text
- 実装は `log/slog` の `NewJSONHandler` / `NewTextHandler` を使う

### フォーマット(フロント側)

- MVP フェーズは `console.*` のまま
- 本番リリース前に Sentry または同等のサービスを導入する(このタイミングで規約を更新)

### リクエスト追跡

- リクエストごとに **リクエスト ID** をミドルウェアで生成
- すべての関連ログに付与する
- フロントから送るリクエストにもヘッダーで ID を付与し、サーバー側のログと突合できるようにする

## 4. 個人情報(PII)・機密情報の扱い

### ログに出してはいけない項目

- メールアドレス、電話番号、住所等の個人識別情報(そのまま出さない)
- パスワード、アクセストークン、API キー、JWT 等の認証情報
- クレジットカード番号、口座番号等の決済情報
- DB の生 SQL クエリ(WHERE 句に PII が含まれる可能性)

### 必要な場合はマスクする

- メール: `a***@example.com`
- 電話: `090-****-1234`
- ID 系: 先頭8文字のみ、または ハッシュ化した値

### 保存・送信時の扱い

- 認証トークンはローカルストレージに**保存しない**(httpOnly cookie を使う)
- 機密情報を含むレスポンスはキャッシュしない(`Cache-Control: no-store`)
- 開発環境のダンプデータでも PII はマスクされたものを使う

│  └──────────────┘   │   RPC   │ │ + Connect   │     │         │              │
│        │            │         │ │   Handler   │     │         │              │
│  ┌──────────────┐   │         │ └──────┬──────┘     │         │              │

│                               │        │            │         │              │
│                               │        v            │         │              │
│                               │ ┌─────────────┐     │         │              │

### 真実の源(Single Source of Truth)

- **API 契約**: `proto/` ファイル
- **DB スキーマ**: マイグレーションファイル
- **業務上の意味のある型**: Go の domain 型定義 / TS の features 内 types.ts

これらは「変更困難な領域」として、変更時には必ず計画提示と確認を行う。

## 6. アンチパターン総合(横断)

### テスト関連

- 数値カバレッジを満たすためだけの無意味なテスト
- 実装の振る舞いをコピーしただけのテスト(AI 罠)
- モックを多用した「実装の中身を確認するだけ」のテスト
- E2E でバリデーションエラーやエッジケースを網羅すること

### ログ関連

- 個人情報・認証情報をそのままログに出す
- エラー発生時にメッセージだけログして、エラーチェーン全体を出さない
- リクエスト ID なしでログを出す(後で追跡できない)

### コメント関連

- what コメントの追加(コードを日本語で言い直しただけ)
- 自明な内容のコメント(関数名と同じ内容を繰り返す)
- 嘘になっているコメント(実装と乖離しているもの)

### アーキテクチャ関連

- 生成物(`gen/` 配下)の手動編集
- proto を変更せずに API レスポンスを変える
- repository / service が Connect エラーを直接返す
- handler が repository を飛び越えて DB 直アクセス
