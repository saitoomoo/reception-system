# PR / Commit Pre-review Checklist

コミット直前・PR 提出前のセルフレビュー用チェックリストです。これまでの規約から導出された確認項目を集約しました。

## 使い方

- すべての項目を毎回確認する必要はありません。**変更内容に応じて該当セクションだけ**チェックしてください
- 「全変更で必ず確認」セクションは、どんなコミットでも目を通してください
- Claude Code に「このチェックリストに照らして実装を見直してください」と依頼することもできます
- このチェックリストに引っかかった項目は、修正してから commit してください

---

## A. 全変更で必ず確認

### コード品質

- [ ] エラーを握り潰していない（`_ = err`、空 catch、`try { ... } catch {}` 等がない）
- [ ] `any` を使っていない（TS）
- [ ] 戻り値 `error` を `_` で捨てていない（Go）
- [ ] **what コメント**（コードを日本語で言い直しただけのコメント）を書いていない
- [ ] マジックナンバー・マジックストリングがない（定数化または列挙型に）
- [ ] 関数が 50 行を超えていない / コンポーネントが 100 行を超えていない
- [ ] ネストが 3 階層以下に保たれている（早期 return で抑える）
- [ ] TODO は `TODO(<担当者またはissue番号>):` 形式で書いている

### 設計思想

- [ ] 不要な抽象化を作っていない（Rule of Three を守っている）
- [ ] 1 つのコードに複数の機能を持たせていない（単一責任）
- [ ] YAGNI 違反していない（必要が見えていないものを先回りで作っていない）
- [ ] 早すぎる最適化をしていない（ホットパス・変更困難領域以外で）

### AI 協働

- [ ] 着手前に計画を提示し、合意を得てから実装した
- [ ] 依頼範囲外のコードを無断で改変していない
- [ ] 機能依存ライブラリを無断で追加していない
- [ ] 「ついでのリファクタ」を勝手にしていない
- [ ] テストが「実装の振る舞いをコピーしただけ」になっていない

---

## B. フロントエンド変更時

### 配置

- [ ] 1 画面でしか使わないコンポーネントは `app/<route>/_components/` に置いた
- [ ] 3 回目以降の利用が発生したら昇格させた（または昇格を計画にメモ）
- [ ] 機能横断の汎用 UI は `components/ui/` に置いた
- [ ] ファイル名が kebab-case になっている

### Server / Client Component

- [ ] デフォルト Server Component を維持している（`'use client'` は必要箇所のみ）
- [ ] Client Component は「インタラクティブな葉」に閉じている
- [ ] Server Component の中で hooks を呼んでいない
- [ ] Server Component を Client Component の子として配置していない（children 経由は OK）

### 状態管理

- [ ] 状態管理判断ルール（1〜4 ステップ）に沿って配置した
- [ ] サーバー状態を `useState` で持っていない（TanStack Query を使う）
- [ ] フォーム状態を `useState` で持っていない（RHF + Zod を使う）

### エラーハンドリング

- [ ] エラーは throw、または Error Boundary で扱っている（Result 型を使っていない）
- [ ] try/catch で握り潰してデフォルト値を返していない
- [ ] `console.error` だけでユーザーに何も表示しないコードがない

### 型

- [ ] `any` を使っていない
- [ ] `as` キャストには理由のコメントがある（DOM 型は除く）

### テスト

- [ ] カスタムフック・純関数にはテストを書いた
- [ ] 表示のみのコンポーネントにテストを書いていない

### Figma Make フロー（取り込み時）

- [ ] App.tsx にすべての画面を詰め込まず、画面単位に分離した
- [ ] 取り込み時に Server / Client の判断を見直した

---

## C. バックエンド変更時

### ディレクトリ・層

- [ ] 機能別ディレクトリに配置した
- [ ] 2 層構成のままで十分か、3 層化が必要か判断した
- [ ] 依存方向が守られている（handler → service → repository）
- [ ] repository が他を呼んでいない

### Connect-RPC

- [ ] proto を変更したら必ず生成物（`gen/`）を再生成した
- [ ] `gen/` 配下を手動編集していない
- [ ] proto コメントを英語で書いた

### エラー

- [ ] errors パッケージで wrap した（`fmt.Errorf("...: %w", err)`）
- [ ] ラップ時の context 文字列に関数名やリソース名を含めた
- [ ] エラーを文字列比較で判別していない
- [ ] ドメイン固有エラーはカスタム型で表現した
- [ ] Connect エラー変換は handler 境界で一括して行った
- [ ] repository / service が Connect エラーを直接返していない

### DB（sqlc + pgx）

- [ ] sqlc 生成型を repository 外部で直接使っていない（ドメイン型に変換した）
- [ ] トランザクション境界が handler または service で決まっている
- [ ] ビジネスロジックを SQL に埋め込んでいない（パフォーマンス上必要な場合を除く）

### ロギング

- [ ] `log/slog` を使っている（`log` パッケージや `fmt.Println` を使っていない）
- [ ] グローバル logger ではなく依存注入している
- [ ] リクエスト ID を関連ログに付与している
- [ ] PII / 認証情報をログに出していない

### テスト

- [ ] 重要箇所（認証・決済・データ整合性）はテストファースト（TDD）で書いた
- [ ] 新規ハンドラには happy path / エラーケース両方のテストを書いた
- [ ] testcontainers-go で実 PostgreSQL を使った（mock や SQLite ではない）

---

## D. CLI / データ処理変更時

- [ ] stdout = データ、stderr = ログ の規約を守っている
- [ ] 進捗バー・ログを stdout に書いていない
- [ ] 起動時に必須環境変数のチェックをしている
- [ ] panic を業務エラーで使っていない（`os.Exit` または error 返却）
- [ ] main 関数にロジックを書かず、テスト可能な関数に分離した
- [ ] `flag` で済むのに cobra を入れていない
- [ ] 設定ファイルにパスワード・トークンをハードコードしていない
- [ ] `.env` を `.gitignore` に含めた / `.env.example` を更新した

---

## E. 設計判断を含む変更

「**変更困難な領域**」を変更する場合、必ず以下を確認:

- [ ] DB スキーマの変更 → 事前確認した、マイグレーションを書いた
- [ ] 公開 API（proto）の変更 → 事前確認した、生成物を更新した
- [ ] 認証・認可ロジックの変更 → 事前確認した、テストを書いた
- [ ] データの ID 体系の変更 → 事前確認した、後方互換性を検討した
- [ ] ログフォーマットの変更 → 事前確認した、既存ログとの整合性を検討した
- [ ] 設計選択肢が複数あった場合、なぜその選択を取ったかを完了報告に書いた
- [ ] 規約に書かれていない判断をした場合、理由を完了報告に書いた

---

## F. コミット直前

- [ ] テストが全部通る
- [ ] lint / 型チェックが通る
- [ ] コミットメッセージが Conventional Commits 形式（`<type>(<scope>): <subject>`）
- [ ] subject は英語、命令形、50 文字以内
- [ ] このコミット単位で独立してロールバック可能
- [ ] 計画段階で提示したコミット案と内容が一致している
- [ ] PII / 機密情報をコミットしていない（`.env`、ログ、ダンプデータ等）

---

## G. PR 提出前（複数コミットをまとめて出すとき）

- [ ] PR タイトルが内容を端的に表している
- [ ] PR 説明に「何を / なぜ / どう」を書いた
- [ ] 動作確認の手順を書いた
- [ ] 影響範囲（破壊的変更の有無、関連するシステム）を書いた
- [ ] レビュアーに見てほしいポイントを明示した
- [ ] スクリーンショット / 録画があれば貼った（UI 変更時）
- [ ] CI が通っている

---

## 補足: Claude Code への依頼テンプレート

このチェックリストを使って Claude Code に自己レビューを依頼するときの例:

```
このコミット案について、@docs/coding/checklist.md の「全変更で必ず確認」「<該当セクション>」
の項目を順にチェックして、引っかかる箇所があれば指摘してください。
引っかからなかった項目は省略して構いません。
```

または特定の観点だけ:

```
@docs/coding/checklist.md の「設計判断を含む変更」セクションに照らして、
今回の変更で漏れている事前確認や説明があれば指摘してください。
```
