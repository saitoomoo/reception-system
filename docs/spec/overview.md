# プロダクト概要

## 1. このプロダクトは何か

大規模イベント(来場者 1,000 人以上が見込まれる)における**受付と整理券管理を Web で完結させるシステム**。来場者はスマホから整理券を取得し、待ち順を確認できる。運営側は QR コードで来場者を捌き、整理券の呼び出し・管理を行う。

イベントの中心となる体験は **HMD(VR ヘッドセット)を装着しての各種体験**。一部のブースは 5 人対戦ゲームなどマッチメイキング型の体験を含む。

## 2. 解決したい課題

- **物理的な待機列だけでは捌ききれない**(1,000 人以上の同時来場が想定される)
- **紙の整理券では呼び出しと待ち時間管理が困難**
- **イベントを運営する複数の係の生徒が、それぞれ自分のブースの予約を管理する必要がある**
- **来場者がブラウザを閉じる・スクショを忘れる等で識別情報を失うリスク**
- **HMD 体験には年齢配慮と保護者同意が必要**で、紙ベースの運用は煩雑

## 3. 想定ユーザー

### 来場者(一般ユーザー)

- イベントに来場する一般客(年齢層: 7 歳以上)
- スマホ(主にブラウザ)で操作する
- 13 歳未満の参加者は保護者同伴を必須とする
- IT リテラシーは高くない可能性が高い → 操作はシンプルである必要がある

### 運営スタッフ(管理者)

- イベントを運営する**生徒**(複数人、ブースごとに担当が異なる)
- 自分の担当ブースの予約状況・整理券呼び出しを管理する
- 全体管理者(1〜数人)が、ブース横断で設定変更や状況確認を行う
- IT スキルにばらつきがある → 直感的な UI が必要

## 4. 主要なユーザーストーリー

### 来場者として

- 受付で名前と PIN を入れて、自分の識別情報(受付番号 + QR)を取得したい
- 興味のあるブースを選んで、整理券を取りたい
- 自分の順番が近づいたら通知を受け取りたい(Web Push、画面 polling)
- 待ち時間や残り人数を確認したい
- 体験後にアンケート(Google Forms)に回答したい
- 万が一スマホでブラウザを閉じても、再度ログインできるようにしたい
- 5 人対戦ゲームでは、自分のグループだけで遊ぶか、他のグループと混ぜるか選びたい

### 運営スタッフとして

- 来場者の QR コードを読み取って入場処理をしたい
- 自分のブースの予約一覧・待ち人数を確認したい
- 通知を呼び出したい来場者に向けて送りたい
- QR が読めない / 忘れた来場者を手動で入場処理できるようにしたい
- 1 日の来場者数や待ち状況を後から CSV で集計したい
- マッチメイキング型のブースでは、人数が揃わない場合に強制開催できるようにしたい

### 全体管理者として

- 各ブースの設定(タイトル・場所・時間・体験タイプ・各種パラメータ)をまとめて管理したい
- 通知メッセージのテンプレート、リスク説明文の文面を編集したい
- システム全体の稼働状況を把握したい
- ブース紹介画像・動画の URL を登録したい

## 5. 技術スタック

| レイヤー | 技術 |
|---|---|
| フロントエンド | Next.js (App Router), TypeScript, shadcn/ui |
| バックエンド | Go (`net/http`), Connect-RPC |
| データベース | PostgreSQL (Neon, サーバーレス) |
| DB アクセス | sqlc + pgx |
| ストレージ | Cloudflare R2 (S3 互換 API、必要に応じて GCS に切替可) |
| 通知 | Web Push (VAPID) + 画面 polling |
| 動画埋め込み | YouTube 限定公開 |
| アンケート | Google Forms (外部リンク) |
| デプロイ | Cloud Run (フロント・バック) |
| API スキーマ | Protocol Buffers (buf + connect-go + connect-es) |

詳細な構成は `infrastructure.md` を参照。

## 6. スコープ

### MVP に含むもの

- 来場者の認証(ニックネーム + PIN による登録 / 受付番号 + PIN による再ログイン)
- 受付番号と QR コードの発行・表示・スクショ促進
- 整理券の取得・予約状況確認(4 種類のブースタイプに対応)
  - 順次体験型 (sequential)
  - 同時並行型 (parallel)
  - 個人体験型 (individual)
  - マッチメイキング型 (matchmaking)
- 13 歳未満の参加者を含む場合の保護者同意フロー
  - 10 歳以上: デジタル同意(レベル 2.5)
  - 7〜9 歳: スタッフ介在の特殊フロー(紙の同意書 + デジタル記録の併用)
- 各ブースの待ち人数・順番表示
- クールダウン機能(同じブースの連続体験を制限、ブースごとに時間設定可)
- pending 状態(呼び出し後 No Show を保留化、復帰時に優先呼び出し)
- 管理画面: ブース設定、予約一覧、QR 読み取り入場処理、手動入場処理、強制開催
- Web Push 通知(申し込み完了、呼び出し、再通知)
- 画面 polling によるフォールバック表示
- CSV 出力
- 来場者向けのイベント情報・ブース紹介ページ
- アンケートへの誘導(Google Forms 外部リンク)

### 将来追加(MVP に含まない)

- LINE 連携(LINE Messaging API)
- 体験後の自動アンケート画面切り替え(優先度は高い)
- 待ち時間の自動グラフ化
- 来場者向けのデータ分析機能
- スタッフの個人アカウント方式への移行
- 多言語対応

### スコープ外

- イベント当日以外での予約(事前予約は受け付けない前提)
- 決済機能
- 来場者間のコミュニケーション機能
- メール通知

## 7. 年齢ポリシー

HMD 体験を含むことを踏まえ、以下のポリシーを採用する。

| 年齢 | 受付 | 同意フロー |
|---|---|---|
| 7 歳未満 | 受付不可 | - |
| 7〜9 歳 | スタッフ介在の特殊フロー | 保護者同伴 + 紙の同意書 + デジタル記録 |
| 10〜12 歳 | オンライン受付可 | 保護者同伴 + デジタル同意(レベル 2.5) |
| 13 歳以上 | オンライン受付可 | 本人同意のみ |

詳細は `domain.md` の業務ルール R-005、`features/ticket.md` の同意フローを参照。

## 8. 非機能要件

- **同時アクセス**: 10,000 人程度の同時アクセスに耐えられること
- **データ保持**: 来場者がブラウザの閲覧履歴を削除しても、サーバー側のデータは消えないこと
- **可用性**: イベント当日の数時間、極めて高い可用性が求められる(代替手段がない)
- **モバイル最適化**: 画面はスマホ最適化が必須(PC は管理者のみ想定)
- **個人情報の最小化**: メールアドレス・本名・住所等は取得しない。来場者の識別情報は受付番号と PIN のみ

## 9. 成功指標

- 来場者がスマホから整理券を取得できること(基本要件)
- 待機列が物理的に滞留しないこと(運営的成功)
- 来場者・スタッフのいずれかがシステムを操作できないケースがほぼ発生しないこと
- 来場者が「呼び出されたのに気づかなかった」というケースが最小化されること
- 7〜12 歳の参加者が、保護者同意フローを通じて適切に体験できること

## 10. 重要な前提事項

### HMD 体験のリスクと運営責任

HMD は健康面の配慮が必要(目の疲労、VR 酔い、転倒等)。本システムは**「運営の善管注意義務を補助する」位置づけ**であり、対面でのスタッフによるリスク説明と装着支援を前提とする。詳細な運営手順は `docs/operation/` 配下のマニュアル(別途整備)を参照。

### システムが扱わない範囲

- 体験中の物理的な事故対応
- 機器の消毒・衛生管理
- 体調不良発生時の応急処置
- 紙の同意書の物理保管

これらは運営マニュアル側で扱う。
