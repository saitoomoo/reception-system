# 機能: 管理者画面

スタッフがブースの予約状況を管理し、入場処理・呼び出し・特殊フロー手動発行を行う画面。共有パスワード方式の認証で、ブースごとに権限を分離する。

---

## 1. 機能概要

イベント運営側のための画面。**ブース担当スタッフ**(各企画の生徒、共有パスワードでログイン)と**全体管理者**(数人の主要運営、専用 ID + パスワードでログイン)の 2 つのロール。スタッフは自分の担当ブースの予約状況を見て呼び出し・入場処理・特殊フロー対応を行う。全体管理者はブース設定の変更や通知テンプレート編集などを行う。

---

## 2. ロール(権限区分)

| ロール | ログイン方式 | できること |
|---|---|---|
| ブース担当スタッフ | ブース別共有パスワード | 自分のブースの予約一覧・呼び出し・入場処理・QR スキャン・特殊フロー手動発行 |
| 全体管理者 | 専用 ID + パスワード | 上記すべて + ブース設定 + 通知テンプレート編集 + リスク説明文編集 + CSV エクスポート + 全体ダッシュボード |

R-011 に従い、**個人特定はせず、ブース粒度の操作ログのみ記録**する。

---

## 3. 主要な画面構成

```
管理者画面
├── ログイン (ブース選択 + パスワード)
├── 全体管理者ログイン (別ルート)
├── ダッシュボード (役割により表示内容が変わる)
│   ├── ブース担当: 自分のブースの状況
│   └── 全体管理者: 全ブース横断の状況
├── ブース運用画面 (担当ブースごと)
│   ├── 予約一覧
│   ├── QR スキャナー
│   ├── 手動入場処理
│   ├── 呼び出し操作
│   ├── マッチ待機列ビュー (matchmaking ブースのみ)
│   ├── 強制開催 (matchmaking ブースのみ)
│   └── 特殊フロー手動発行 (7〜9 歳対応)
├── ブース設定 (全体管理者のみ)
├── 通知テンプレート編集 (全体管理者のみ)
├── リスク説明文編集 (全体管理者のみ)
└── CSV エクスポート (全体管理者のみ)
```

## 4. ログイン

### 4-1. ブース担当スタッフのログイン

#### 画面構成

- ブース選択(プルダウン or カード形式)
- パスワード入力(該当ブースの共有パスワード)
- 「ログイン」ボタン

#### 処理

1. ブース ID とパスワードをサーバーに送信
2. サーバー側で `booths.staff_password_hash` と照合
3. 一致したら、そのブースのみ操作可能なセッションを開始
4. クッキーまたは JWT で `booth_id` を埋め込む

### 4-2. 全体管理者のログイン

#### 画面構成

- 別 URL(例: `/admin/global/login`)
- ID + パスワード入力

#### 処理

1. ID とパスワードを `global_admins` テーブルと照合
2. 成功時、全権セッションを開始

---

## 5. ダッシュボード

### 5-1. ブース担当スタッフのダッシュボード

ログイン後、自分のブースの状況が表示される。

- ブース名
- 現在の待ち人数
- 本日の入場済み人数
- 直近で呼び出した整理券
- 「ブース運用画面に進む」ボタン

複数ブースの担当パスワードを別々に持っていれば、それぞれ別ログインする想定。

### 5-2. 全体管理者のダッシュボード

- 全ブースの状況を一覧表示
- 各ブースの:
  - 体験タイプ(バッジ表示)
  - 待ち人数 / 入場済み人数
  - 推定処理速度(待ち時間の長期化を察知)
- 全体の来場者数
- グラフ表示(将来。MVP では数値のみで OK)

## 6. ブース運用画面

各ブース担当が常時開いておく画面。タブレット or スマホで使う想定。体験タイプによって表示が変わる。

### 6-1. 予約一覧(共通)

- そのブースの整理券を一覧表示
- 状態でフィルタ可能(`waiting` / `called` / `pending` / `admitted`)
- 各行に表示する情報:
  - 整理券番号 / 来場者の受付番号 / 代表者ニックネーム / 体験人数 / ステータス / 取得時刻
- 行タップで詳細表示
- 操作ボタン:
  - 「呼び出す」(`waiting` → `called`)
  - 「入場処理」(`called` → `admitted`、QR が読めない時の手動操作)
  - 「キャンセル」(運営判断のキャンセル)

#### 優先呼び出しの表示

`is_priority_call = true` の整理券は、リストの上部に「**優先呼び出し**」セクションで表示する(R-013)。スタッフが現在体験中の人が終わったらすぐ次に処理できるよう、視覚的に強調。

```
[優先呼び出し]
  - T-105 (戻ってきた来場者) ← 強調表示

[呼び出し中]
  - T-103
  - T-104

[待機中] x 5

[保留中(pending)] x 2
```

### 6-2. QR スキャナー

- カメラを起動して QR コードを読み取る画面
- スキャン成功時:
  1. QR から受付番号を抽出
  2. その来場者の、自ブースの整理券を検索
  3. 状態を確認:
     - `waiting`: 「呼び出される前の入場ですが処理しますか?」と確認
     - `called`: そのまま入場処理(`admitted` に遷移)
     - `pending`: `called` に戻して `is_priority_call = true` を立てる(R-013)、その後通常の入場処理画面へ
     - `admitted`: 「既に入場済みです」と表示
     - 整理券なし: 「整理券が見つかりません」と表示
- スキャン失敗時: エラー表示と再試行ボタン

### 6-3. 手動入場処理

QR が読めない来場者向け。

入力:
- 受付番号(`A-105` 形式)

処理:
- 自ブースの整理券を検索して入場処理
- 整理券がない場合は、その場で発行する選択肢も提示(運営柔軟性のため)
- pending 状態だった場合は QR スキャンと同じ処理(復帰 + 優先付き)

### 6-4. 呼び出し操作

- 「先頭の整理券を呼び出す」ボタン
- 一括で N 件呼び出すオプション(R-008 の `call_threshold` を目安)
- 呼び出された来場者には Web Push 通知が送られる

### 6-5. マッチ待機列ビュー(matchmaking ブースのみ)

`features/match.md` 参照。

```
[現在のマッチ待機 (public)]
  累積人数: 3 / 5
  - T-103 (山田家、3人)
  - T-105 (ソロ、1人)
  → あと 2 人で開催可能
  [強制開催ボタン]

[現在のマッチ待機 (private)]
  - T-101 (鈴木家、4人) [呼び出しボタン]

[体験中]
  - Session #45 (5人、14:30 開始)
```

#### 強制開催の確認

- ボタン押下時に確認モーダル
- 「現在 X 人で開催します。よろしいですか?」
- 確認後、`min_party_size` チェックを実行

### 6-6. 特殊フロー手動発行(7〜9 歳対応)

R-005 の特殊フロー。来場者が 7〜9 歳の場合、オンラインで整理券を取得できないので、ブースで対面処理する。

#### フロー

1. 保護者と参加者(7〜9 歳)がブースに来る
2. スタッフが「特殊フロー手動発行」ボタンを押す
3. 紙の同意書を保護者に手渡し、記入してもらう
4. 並行して、スタッフ用タブレットで以下を入力:
   - 来場者の受付番号(QR スキャン or 手入力)
   - 体験人数
   - 各参加者の年齢・氏名
   - 保護者氏名
   - 紙の同意書の管理 ID(連番、印刷時に振っておく)
5. リスク説明文を保護者に読んでもらう(タブレット画面で)
6. 保護者がスタッフ用タブレットで「同意」ボタンを押す
7. システム側で整理券を発行(`consent_method = 'paper_and_digital'`)
8. 紙の同意書はスタッフが回収して保管(運営マニュアル側で管理)

#### スタッフ画面のフォーム例

```
特殊フロー手動発行
  来場者の受付番号: [QR スキャン] [A-105]
  体験人数: [3]
  各参加者:
    1. 名前: [太郎]    年齢: [8]   ← 7-9 歳該当
    2. 名前: [花子]    年齢: [10]
    3. 名前: [次郎]    年齢: [42]  保護者
  保護者氏名: [山田 一郎]
  紙の同意書 ID: [P-0042]
  
  [リスク説明文を表示]  ← 保護者に見せる
  
  [✓ 保護者が同意した]
  [整理券を発行]
```

## 7. ブース設定画面(全体管理者のみ)

### ブースごとに編集可能な項目

| 項目 | 説明 |
|---|---|
| ブース名 | 表示用の名称 |
| 説明 | ブース紹介テキスト |
| 開催場所 | 物理的な場所 |
| 開催日 / 時間帯 | 受付可能な時間帯 |
| 体験タイプ | sequential / parallel / individual / matchmaking |
| 1 整理券あたりの最大人数 | `max_participants_per_ticket` |
| 同時並行可能人数 | `concurrent_capacity`(parallel のみ) |
| 理想の開催人数 | `target_party_size`(matchmaking のみ) |
| 最低開催人数 | `min_party_size`(matchmaking のみ) |
| プライベートマッチ可 | `allow_private_match`(matchmaking のみ) |
| 1 人あたりの体験時間 | `estimated_minutes_per_person` |
| 1 セッションの時間 | `estimated_minutes_per_session`(parallel/matchmaking) |
| 呼び出しタイミング目安 | `call_threshold` |
| 呼び出し再送/pending 遷移時間 | `call_resend_minutes` |
| クールダウン時間 | `cooldown_minutes`(0 で無効) |
| 整理券発行可否 | `is_accepting`(一時停止スイッチ) |
| 共有パスワード | `staff_password_hash`(変更時はパスワードを再入力) |
| 紹介画像 | `cover_image_url`(R2 にアップロード) |
| 紹介動画 | `intro_video_url`(YouTube URL) |
| アンケート URL | `survey_url`(Google Forms 等) |

### 画像アップロード

- 「画像を選択」ボタンで端末からファイル選択
- バックエンド経由で R2 に保存(`infrastructure.md` 参照)
- 保存後、`cover_image_url` を更新
- バリデーション: JPEG/PNG/WebP、5 MB 以下、サイズ 4096px 以下

### 動画 URL の登録

- YouTube URL のみ受け付ける(`youtube.com` または `youtu.be`)
- 限定公開推奨を案内
- 埋め込み可能か事前確認(API での確認は MVP では不要、運営側で確認)

### パスワード変更

- 「パスワードを変更」ボタンで再入力フォーム表示
- 旧パスワード確認は不要(全体管理者の権限で変更)
- 変更時は `staff_password_updated_at` を更新

## 8. 通知テンプレート編集(全体管理者のみ)

### テンプレートの構造

| キー | 用途 |
|---|---|
| `application_completed` | 整理券取得完了時 |
| `call_initial` | 初回呼び出し |
| `call_resent` | pending 遷移時の再通知 |
| `cancelled_by_staff` | 運営側がキャンセルした時(任意) |

### 編集項目

- タイトル(Push 通知のタイトル、目安 30 文字以内)
- 本文(Push 通知の本文、目安 100 文字以内)
- アイコン URL(任意、R2 から)

### 変数の埋め込み

`{{ニックネーム}}`, `{{ブース名}}`, `{{受付番号}}`, `{{整理券番号}}`, `{{場所}}` 等の変数を使える。バリデーション: 不明な変数を使うとエラー。

---

## 9. リスク説明文編集(全体管理者のみ)

`risk_explanations` テーブルの本文を編集する画面。

- 現在の本文を表示
- リッチテキストではなくプレーンテキスト(Markdown 程度の構造化は可)
- 「保存」ボタンで `updated_at` を更新
- 過去の同意記録(`parental_consents.consent_text_snapshot`)には影響しない

## 10. CSV エクスポート(全体管理者のみ)

### エクスポート対象

| データ | 用途 |
|---|---|
| 来場者一覧 | 受付番号、登録時刻、ニックネーム |
| 整理券一覧 | 全整理券の取得・状態・入場時刻 |
| 入場処理一覧 | admissions テーブル全件 |
| ブース別集計 | ブースごとの予約数・入場数・キャンセル数 |
| マッチセッション一覧 | matchmaking ブースのセッション履歴 |
| 時間帯別集計 | 30 分ごとの来場者数推移 |
| 通知配信ログ | notification_logs(マスク済み) |

### エクスポート形式

- CSV(UTF-8 / BOM 付きで Excel が文字化けしないように)
- ファイル名は `<種類>_<日時>.csv` 形式
- 個人情報を含むため、ダウンロード時に確認画面を挟む
- ダウンロードログを残す(誰がいつ何をダウンロードしたか、これは未実装の課題として残す)

## 11. 認証・認可

### スタッフセッション

- ログイン成功時、`booth_id` をクッキーまたは JWT に埋め込む
- 各 API 呼び出し時に、操作対象ブースとセッションの `booth_id` の一致を確認
- 不一致なら `connect.CodePermissionDenied` を返す

### 全体管理者セッション

- ログイン成功時、`role: 'global_admin'` をセッションに埋め込む
- 全 API へのアクセス可

### セキュリティ補足

- 共有パスワードは bcrypt でハッシュ化
- パスワードはイベントごとに変更(終了後にハッシュをローテーション)
- 不正試行が増えた場合の対策(レート制限等)は MVP では未実装、運用で検出

## 12. エラーケースと UX

| エラー | UX |
|---|---|
| QR スキャン失敗 | 「読み取れませんでした、もう一度お試しください」 |
| 入場済み整理券をスキャン | 「既に入場済みです」(エラーではなく情報表示) |
| 別ブースの整理券をスキャン | 「このブースの整理券ではありません」 |
| ネットワーク失敗(操作系) | 「保留中」状態で再送試行、明示的にエラー表示 |
| 同時に同じ整理券を 2 人が処理 | 楽観ロックでどちらか一方が失敗、リフレッシュを促す |
| 強制開催で人数不足 | 「最低 N 人必要です」 |
| 共有パスワード不一致 | 「パスワードが違います」 |

## 13. テスト方針

管理者画面の入場処理は**重要箇所**(誤操作が運営の信頼に直結する)。

- QR スキャンによる入場処理: TDD で書く
- 手動入場処理: TDD で書く
- 重複入場の防止: TDD で書く
- 特殊フロー手動発行: TDD で書く(複雑なフロー)
- pending からの復帰時の優先呼び出し: TDD で書く
- 呼び出し操作: アフターで OK
- ダッシュボード集計: アフターで OK
- CSV エクスポート: アフターで OK
- 強制開催: TDD で書く(matchmaking 関連)

E2E で押さえるべき動線:

- スタッフログイン → ブース運用画面 → QR スキャン → 入場処理
- 全体管理者ログイン → ブース設定 → 設定変更が反映されるか
- 特殊フロー手動発行(7〜9 歳の保護者対応)
- pending 状態の整理券が QR スキャンで復帰
